## Secret Chats — credential-gated locked space (2026-07-26, commit `4195372`)

**What it is:** a second, independent privacy layer inside the app (the main biometric app lock is untouched). Chats locked into it are invisible everywhere in normal UI and guarded by a knowledge-only secret code — PIN, pattern, or password; deliberately NO biometric/device-credential path (biometrics on shared phones can belong to other people), NO recovery path.

**Data model:** Room v7→v8 — `space` TEXT ('NORMAL'/'LOCKED') on `messages` + `conversations`; the conversations unique index widened to `(threadId, space)` so "New locked chat" keeps a second conversation row for the same system thread. Provider untouched (SMS stays in shared storage — stated verbatim in the setup disclaimer + README). Every DAO query feeding normal UI pins `space='NORMAL'` (home list/folders, FTS + LIKE + name search, suggested chips (derive from filtered results), starred, Trash screen, unread badges, widgets, dashboard stats, badge metadata, forward picker); chat-serving queries take a `:space` param; background maintenance (trash purge, OTP/spam cleanup, FTS renormalize) deliberately spans both. `SpaceInvisibilityTest` (9 DAO tests) locks the contract.

**Credential (`core-messaging/secret/`):** `SecretCrypto` (pure JVM) — PBKDF2-HMAC-SHA256 600k, salted 256-bit verifier + a SEPARATELY-salted KEK for backups; constant-time verify; pattern = ordered distinct 3×3 cells (≥4). `SecretCooldown` — 5 free attempts, then 30s/1m/5m/15m/60m escalating cooldown from the last failure (resets only on success). `SecretSpace` — prefs store (`secret_space`), Keystore-encrypted KEK cache (`LocalKeyBox`, plain fallback for JVM tests), change-credential (requires current, re-keys), notification mode, pending-restore state. `SecretCredentialTest` (9 tests).

**Routing rule (the invisibility keystone):** `MessageRepository.spaceForIncoming` — once a LOCKED conversation exists for a thread, ALL incoming SMS/MMS from that address are written with `space=LOCKED` and update only the locked conversation. The classifier runs normally first (locked space has its own folder chips; spam from a locked sender lands in the locked Spam, not normal Spam). `LockedRoutingTest` covers create→route→classify→unlock→revert end-to-end through the real pipeline.

**Notifications:** locked-space messages → ONE fixed-id (−200) generic notification, title "Messages", text "New message", CH_PERSONAL, no person/photo/shortcut/bubble/reply/OTP-hero/badge/subtext, content intent opens Home (never the chat). Per-space setting can silence entirely (Generic/Off). Spam/promo/review from locked senders never notify; the red fraud warning is suppressed for locked messages (would betray the space). Locking removes shortcut + per-conversation channel + any visible notification (`removeLauncherIdentity`). Snooze reminders for locked messages carry no sender/content/deep-link.

**UI (`app/ui/secret/`):** entry = 3s press-and-hold on the Home "Messages" title (custom pointerInput timer — combinedClickable's ~400ms long-press is too discoverable), no visual affordance. First time → `SecretSetupScreen` (kind chooser → confirm → disclaimer with the spec's VERBATIM text, must scroll to end before "I understand" enables); after → `SecretPromptScreen` (live cooldown countdown, "no recovery" footer). `LockedSpaceScreen` mirrors Home (54dp avatar rows, folder chips + unread from LOCKED queries); row long-press → move-back/mute sheet; in-space `SecretSettingsScreen` (change code, notification behavior). Chat ⋮ → "Lock chat" bottom sheet ("New locked chat" / "Move entire chat" — honest supporting text each) in normal space, "Unlock chat" inside. Re-lock is IMMEDIATE: `SecretSession.lock()` on Activity `onStop` (no grace ever, external-trip suppression deliberately NOT honored) and on navigating to any non-secret route; every secret route bounces to Home when the session isn't unlocked; FLAG_SECURE forced while any secret route shows. Locked chats skip DraftStore (drafts are keyed by threadId — a locked draft would surface as "Draft:" on the normal row of the same thread), skip shortcuts/report-used, and suppress MMS-attach paths through `space`-aware `storeOutgoing*`/`MmsSender`.

**Backup (`BackupManager` + `BackupCrypto`):** locked rows leave the plaintext payload entirely; they travel as `lockedEnvelope` — a standard MBK1 envelope whose data key is wrapped with `wrapWithKek` (the cached credential-KEK) recorded as a METHOD_PASSWORD wrap carrying salt_k + 600k, so restore-side unlock is literally the existing `openWithPassword(blob, enteredCredential)` path. `lockedAuth` (verifier + both salts + iterations + kind) travels alongside so a fresh device can run the prompt. Import: same-credential devices open immediately (cached KEK); otherwise the envelope is stashed (`secret_pending.mbk`) and the UI shows "Locked chats present — enter your secret code to unlock" (restore toast + prompt copy); first successful entry adopts the carried auth, derives the KEK, imports into the LOCKED space, and recreates routing rows for every locked address (even message-less "New locked chat" ones). Dedupe key set spans BOTH spaces. A still-pending envelope is carried forward verbatim by the next backup (restore→backup chains never drop locked data). KEK-cache-lost corner: that snapshot ships without locked chats (never plaintext); next unlock re-caches and the next snapshot carries them. `LockedBackupTest`: round-trip, plaintext-leak assertion, wrong-credential rejection, fresh-device pending flow, placement, idempotent re-import.

**Legacy migration:** first secret-space setup calls `migrateLegacyLockedConversations()` — old biometric-locked (`locked=1`) threads move into the locked space (disclaimer step says "Your existing locked chats will move here" when any exist) and the flag clears. - **Symptom**: on a physical device, Google sign-in for Drive backup appeared to complete (the account picker closed normally, no crash) but the app never registered it — `DriveBackupScreen` stayed stuck on "Choose Google account" instead of showing the signed-in state.
- **Three compounding bugs found via on-device logcat diagnostics, fixed in order:**
  1. **Touch/launch storm**: a single physical tap on the sign-in button was firing the `ActivityResultContracts.StartActivityForResult()` launcher dozens of times (some callbacks landing 1–3ms apart — physically impossible for one tap), producing overlapping sign-in attempts and racing `ApiException` 12502 (`SIGN_IN_CURRENTLY_IN_PROGRESS`) failures mixed with silent successes. ## Decisions made that are not in the PRD

1. **Stage-2 protected-lane gating**: §5.7 says bank/delivery/bill protection applies from registered headers. Implemented as: OTP patterns protect from **any** sender (absolute, per §5.7); BANK/DELIVERY/BILL/TRAVEL/GOV patterns ride the protected lane only when the sender is a registered DLT header, alphanumeric header, short code, or saved contact — a personal/international number saying "your parcel shipped, pay fee" falls through to scoring. This closed a real bypass found in testing (gift-parcel scam from +1 number matching "shipped").
2. **Leet-map safety rule**: leet substitution applies per token, only when letters ≥ digits, and symbol leets (`@ $ !`) convert only when followed by a letter — so "Offer!" keeps its `!`, OTP digits and `₹5,000` amounts are never rewritten.
3. **Repeated-char collapse restricted to letters** — collapsing digits corrupted amounts/OTPs ("4,999"→"4,99").
4. **KBC pattern requires amount/link/call context** (not the bare word "KBC") so TV-show chatter from friends isn't flagged; same philosophy applied to "digital arrest" (negative-lookahead for "scam" so articles *about* the scam don't match), "sasta"→"sabse sasta", etc.
5. **Engine library JSON id/family conventions**: families are kebab-case strings centralized in `Families`; link/format signals are synthetic pattern IDs (`link-shortener`, `format-caps`…) so the Why? screen can explain them uniformly.
6. **Room is an index, Telephony provider is source of truth** (per §10); incoming messages are written to the provider *before* classification so a crash mid-pipeline can't lose a message.
7. **Thresholds**: Sensitivity presets RELAXED (18/13/7) and STRICT (12/8/4) around the PRD's DEFAULT (15/10/5). C10 promo-pileup routes to Promotions even when raw score < review threshold.
8. **`fallbackToDestructiveMigration()`** on the Room index during development — acceptable only because the Telephony provider holds the real data; must be replaced with real migrations before release.
9. **Versions**: minSdk 26, targetSdk/compileSdk 35, Kotlin 2.0.20, AGP 8.5.2 with Gradle 8.9 (system Gradle 9.6 is incompatible with AGP 8.5 — always use `./gradlew`).
10. **MMS receive**: hand-rolled minimal WSP/MMS PDU parser (`MmsPduParser`) instead of a library — parses only the two PDUs a receiver sees (m-notification-ind, m-retrieve-conf), skips unknown headers via the generic WSP rule, and now records a recoverable placeholder for malformed or unavailable deliveries. No m-notifyresp-ind ack is sent; carrier redelivery is handled by transaction-ID dedupe instead. MMS send is implemented separately in `MmsPduBuilder`/`MmsSender`.
11. **Sensitivity setting** lives in SharedPreferences `"settings"` (key `sensitivity` = DEFAULT|RELAXED|STRICT); an imported pattern pack is persisted as `filesDir/patterns_imported.json` and wholesale-replaces the bundled library at engine creation (revert deletes the file and hot-reloads bundled).
12. **MMS send**: hand-rolled `MmsPduBuilder` (m-send-req only), symmetric with the parser. From-header uses insert-address-token (MMSC fills our number). Images are recompressed to ≤1MB/≤1440px JPEG before send; oversized non-images are rejected with a snackbar rather than sent and carrier-bounced.
13. **Group thread convention**: a group is addressed as `;`-joined recipient numbers in `ConversationEntity.address` / `MessageEntity` fallback routes; `recipientsOf()` splits it everywhere. Incoming group MMS identifies co-recipients from To/CC and drops our own numbers by comparing the last 10 digits (SubscriptionManager numbers are often blank — then the group thread degrades to 1:1 with the sender, acceptable).
14. **Dual-SIM**: per-chat choice persisted on the conversation row (`preferredSubId`, null = system default); the picker only renders with ≥2 active subscriptions. Sends go through `SmsManager.createForSubscriptionId`; group SMS status still shares one PendingIntent (same debt as multipart, below).
15. **OTP auto-delete scope**: DAO query additionally excludes **starred** OTPs (user explicitly kept them) — slightly stricter than the PRD's "OTP-labeled Inbox messages". The DAO `userDelete` comment documents the §6.5 cleanup as its only non-user caller.
16. **Scheduled send is index-only until fire time**: the Telephony provider is written only when the message actually sends (other apps must not see unsent messages as Sent). Snooze is a WorkManager one-shot that re-posts a notification; nothing is stored on the message row. Scheduled MMS not supported (schedule button hides while an attachment is staged).
17. **App lock re-locks on every `onStop`** (no grace period) — external flows (camera capture, role dialogs) re-prompt on return; accepted for v1. App-lock state is deliberately excluded from backup restore (device-specific auth hardware).
18. **Widgets are classic RemoteViews** (no Glance/ListView) — static text lines, updated by push (`WidgetUpdater`) + 30-min system cycle.
19. **Backup restore is additive-only** per §6: never deletes/overwrites; dedupe key is address+timestamp+direction+body-hash; reputations only fill senders with no local record; rules dedupe by kind+target+pattern.
20. **Trash semantics (§6.4)**: trashing removes the provider row immediately (other SMS apps must not still show a "deleted" message) while the Room index row keeps the content for the 60-day window; restore re-creates the provider row (new smsId). Trashed OTPs are excluded from §6.6 auto-cleanup — the user's trash intent wins, keeping the restore window. Hard-delete (`userDelete`) has exactly 4 callers: Delete forever, 60-day purge, OTP cleanup, cancelling a scheduled draft.
21. **FTS multi-keyword strategy (§8.5)**: one FTS prefix query per keyword merged in Kotlin instead of FTS `OR` syntax (enhanced-query support varies by OEM SQLite); this also yields per-keyword match info used for ranking ("Matches k of n") and highlighting. Migration leaves old rows' `normalizedBody` empty as a backfill sentinel; `FtsRenormalizeWorker` fills them once with the engine normalizer.
22. **Drive key model (§8.3)** — *revised 2026-07-22 to the WhatsApp-style account model*: a 256-bit master key lives in a key file (`messages-backup-key.bin`) in the same Drive appDataFolder as the snapshots; each snapshot's fresh random data key is wrapped under it (`account-plain` method in the versioned `wrappedKeys[]`). Access to the Google account IS the access control; restore needs no user input. The Drive key file is authoritative (a restore on another device must find it); a local Android-Keystore-encrypted cache is the fallback/re-upload source. The snapshot prune filter (`.mbk` only) can never delete the key file. Legacy `password`-wrapped envelopes are detected via `BackupCrypto.requiresPassword(header)` and prompt for their original password. Honest trade-off, stated openly: anyone who can sign in to the Google account can decrypt backups — same custody model as WhatsApp's default; the envelope still protects against Drive-side snooping without account access. Passkey-PRF remains format-reserved (needs a hosted RP domain — no server exists per §2.2).
23. **Drive scheduling (§8.3)**: WhatsApp-style checkpoints — snapshot content is "everything up to the last 6:00 AM checkpoint" for the chosen frequency, regardless of when WorkManager runs; a 6-hourly worker no-ops until a new window passes. Manual backups checkpoint at `now`. Last 2 snapshots kept in `appDataFolder`.
24. **Bubbles/shortcuts privacy**: locked conversations never get shortcuts (removed on lock) and never bubble; bubbles are also suppressed entirely while app lock is enabled (a bubble would bypass the biometric gate). Custom spam-backup selection is stored as message-id StringSet in `drive_backup` prefs (device-local; ids are not stable across restores — acceptable, the selection is a this-device concern).
